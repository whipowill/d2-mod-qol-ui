# qol_ui: detailed notes

Reference material that used to live in `CLAUDE.md`: where things are, game offsets and structures, how each feature was ported from BH, and the pitfalls found on the way.
It is not loaded automatically (to keep the session context small); read the section you need. Build / test commands and the conventions are in `CLAUDE.md`.

## Source map
`qol_ui.c` unity-includes the headers below, in this order: `lootfilter.h`, `automap.h`, `hud.h` (includes `stats.h`), `idclick.h`, `keys.h`. Order matters (statics are shared).
- `src/qol_ui.c`: DllMain, config (`load_config`, re-callable by the reload key), log + crash handler, Storm file reads (`storm_read`), patch helpers (`patch_bytes`, `stub_alloc`, `emit`, `emit_rel`), `readable()` / `readable_c()` (cached variant for hot loops, `readable_reset()` first).
- `src/filter.c/h`: ItemDisplay rule engine, pure C. `fi_parse`, `fi_name`, `fi_desc`, `fi_actions`, `fi_is_blocked`; the caller fills an `fi_item`.
- `src/itemdb.c/h`: reads ItemTypes/Armor/Weapons/Misc.txt (through Storm, so mods are followed) into item groups, tier bits, levels, speed, rune number, gem level/type.
- `src/sig.h`: byte-signature search (`qt_find`, -1 = wildcard) and the site finders `sig_find_itemname`, `sig_find_gameloop`, `sig_find_automap`, `sig_find_gamedraw`. Each returns the offset or -1 unless exactly one match (original or already patched).
- `src/lootfilter.h`: item-name hook + per-item name cache, game-memory side of the engine (`mh_fill_item`), game-loop hook (`mh_install_loop`, `mh_game_loop` calls `am_loop`, `id_tick`, prints queued chat), drop alerts + item map-dot table (`g_dots`).
- `src/automap.h` + `src/atvectors.h`: automap hook (tail of the automap draw), destination lines, cross colours, the game's own map text is hidden here.
- `src/hud.h`: GameDraw tail hook; clock (map closed) / map info (map open); calls `stats_draw`. Texts are built when they change and cached.
- `src/stats.h`: the character stats panel.
- `src/buffs.h`: buff / aura / debuff icons (see Stats panel, hud ... below).
- `src/idclick.h`: shift-click identify (window subclass for WM_LBUTTONDOWN + `id_tick`).
- `src/keys.h`: key thread (GetAsyncKeyState, only when the game window has focus, in a game, chat closed): reload, filter level +/-, stats, Esc.
- `test/`: `filter_test.c`, `itemdb_test.c`, `sigtest.c` (hex-buffer signature checks for all four site finders, driven from `test.sh`).

## Colours that only work in Glide (found the hard way)
`%CORAL% %SAGE% %TEAL% %LIGHT_GRAY%` are colour codes built from control characters (`\xFF c \x06 / \x07 / \x09 / \x0C`). BH (`ItemDisplay.cpp`, "Revert to non-glide colors") keeps them only when the video mode (WORD at D2gfx +0x14A38; 4 = Glide, which d2gl reports) is Glide and otherwise replaces them with red / green / blue / gray. We passed "not Glide" for a long time (`fi_set_video(s, 0)`), so those four always showed as plain colours; `mh_video_glide()` now reads the real mode before every name evaluation.

## Rule syntax (BH-compatible; the engine matches BH's behaviour)
- `ItemDisplay[conds]: text // comment`; also `ConditionGroup[name]`, `ClassSkillsList`, `TabSkillsList`; other lines ignored.
- Conditions are split on spaces, with leading/trailing `! ( )` peeled off. Key/value splits at `<`, `=`, `>`. Adjacent operands are an implicit AND. AND and OR have
  **equal** precedence and evaluate left to right. Unknown tokens are ignored; a rule made only of unknown tokens matches nothing (`dead`; BH would match everything).
- `COUNT=n,cond,cond`; `ConditionGroup[name]` expands to `( ... )`.
- Text actions: `%NAME%` (name so far), colour macros, `%CONTINUE%`, `%TIER-n%`, `%DOT-xx%` / border / map / px / line / notify colours, `{description}`, `%NOTRACK%`.
- Lists: name rules (visible text), desc, map, ignore (no name/map/desc, stops), whitelist (name rule with stop, no map). "Blocked" = an ignore rule matches, no map
  action matches, and nothing whitelists it. BH appends " [blocked]" to the name AND keeps the item out of the game: `ItemMover::OnGamePacketRecv` (`BH/Modules/ItemMover/ItemMover.cpp`, case 0x9c) parses each incoming ground-item packet (`ParseItem`), evaluates the rules against the packet data and blocks the packet when an ignore rule matches with no map rule and no whitelist, so the client never creates the item. **We do it differently (cheaper, no packet hook, no packet parser; confirmed working in game):** the ground scan already evaluates every new item against the real unit; for a blocked item (`fi_is_blocked`, mode 3/5) it calls the client's own handler for the server packet 0x0A "remove unit" (D2Client +0x83730, fastcall, ECX = `{0x0A, 4, uid}`; packet table at +0xEF4B0, 12 bytes per entry: handler, size, extra) which removes the unit exactly as if the server had. The item can be visible for up to the scan interval (100 ms). The name hook also blanks blocked ground labels as a fallback. Gold piles are never removed (you still walk over them). Their label is NOT built by `GetItemName`: the ground-label builder (D2Client +0x19980; it compares item codes for the quest-item colours, then for item class 4 = gold reads item stat 14, formats it with `%i`, appends a space and "Gold") draws it with one D2Win DrawText call at D2Client +0x19AB5 (`sig_find_golddraw`, the only change is that call's rel32). `mh_install_gold` points it at a stub that calls `mh_gold_skip(text)` first (confirmed working in game; it was the SECOND hook that did the job): the same builder has a second exit where the caller wants the TEXT, not a drawing (D2Client +0x19AEC `lea edx,[esp+34h] ; mov ecx,esi ; call ebp`, `sig_find_goldcopy`, 8 bytes replaced by `E8 rel32 90 90 90`, stub calls `mh_gold_blank` which empties the buffer before the copy) - the ground labels use that one, so both exits are hooked. The decision: `show_gold_amount=0` skips every gold label, otherwise the amount is read back out of the text and the rules are asked (`GOLD<n` / `GOLD>n` compare the pile size; a matching ignore rule skips the draw). Found by logging: the name hook never saw a gold pile. BH can only evaluate GOLD from the packet. (An earlier version of this note wrongly said BH only appends the tag.)

## Game facts (1.13d)
- Item name hook: D2Client RVA 0x96736, 6 bytes `8A 85 2A 01 00 00` (`mov al,[ebp+0x12a]`) replaced by `E8 rel32 90` to a stub that pushes ebx (item unit) and edi
  (wide name buffer) and calls cdecl `mh_item_name(name, item)`, then does `mov al,[ebp+0x12a]` and returns. Signature unique in stock D2Client.
- Unit: +4 txtfileno, +0x14 pItemData. ItemData: quality +0, flags +0x18 (identified 0x10, ethereal 0x400000, runeword 0x4000000), fileindex +0x28, ilvl +0x2c.
  ItemText record (D2Common #10994): item code at +0x80, locale name number at +0xF4. Stat entry: `{WORD sub; WORD index; DWORD value}`.
- D2Common ordinals: GetItemText 10994, GetUnitStat 10550, GetStatList 10449, CopyStatList 10195, GetItemLevelRequirement 10929. D2Lang GetLocaleText 10004 (fastcall).
- D2Client RVAs: GetPlayerUnit 0x613C0, GetDifficulty 0x42980, PrintGameString 0x75EB0 (stdcall wchar*, colour).
- Hook sites (all found by signature, all verified against stock bytes): game loop D2Client +0x45280 (7 bytes, `sub esp,20 ; mov [esp+0C],ecx`); GameDraw tail +0x1D7B4 (`pop esi ; pop ebx ; pop ecx ; ret 4`, 6 bytes -> `E9 rel32 90`); automap-draw tail +0x7349A (9 bytes `8B CF 5F 5E E9 rel32` -> `E9 rel32` + 4 NOPs; the stub redoes them and jumps on).
- The game's own map texts are five `call`s inside the automap draw: area name 0x709E0 (call at site-44), version 0x70900 (-39), game name 0x70790 (-34), 0x70880 (-19), 0x70A30 (-5). `am` NOPs each after checking its target. Each is a plain void routine; `[cf80]` is just a running y position.
- Misc D2Client: UI state array at +0x11C890 (index: inventory 1, chat 5, cube 0x1A, stash 0x19, merc 0x24; automap open flag +0x11C8B8); mouse x +0x11C950, y +0x11C94C; screen width +0xF7034; layouts inventory +0x1016F0, stash +0x1015E0, cube +0x1016D8 (`{BYTE slotW,slotH; DWORD left,right,top,bottom; BYTE pixelW,pixelH}` at +0/+4/+8/+0xC/+0x10/+0x14/+0x15); GetLevelName +0x18250 takes the level in **ESI** (call it through a thunk that does pushad/mov esi/call/popad); DrawRectFrame +0x17D10 takes a RECT* in **EAX**; GetMercUnit +0x9C0A0; GetCursorItem +0x144A0; GetLocaleText wrapper etc. are in BH's D2Ptrs.
- D2Win (by ordinal): DrawText 10076 (fastcall wchar*, x, y, colour, 0), SetTextSize 10047 (fastcall, returns old), GetTextWidthFileNo 10179 (fastcall wchar*, &width, &fileno). D2gfx: DrawLine 10013, DrawRectangle 10028 (trans 7 = BH "highlight", 4 = black). D2Net: SendPacket 10015 (stdcall len, 1/0, bytes). D2Common: GetLevelText 10142 (Levels.txt row; MonLvlEx at +0x16, per difficulty), AddRoomData 10890 / RemoveRoomData 10208 (stdcall act, level, x, y, room1).
- Cross colours: a byte table at D2Client +0x11CF74..: 74 = you, 75 = units you own when you are not in a party (merc, minions), 78 = same when you are, 77 = other players in your party (`team_color`, defaults to `me_color`), 75 also = other players NOT in your party (`other_player_color`, defaults to `npc_color`; shared with minions when you are in no party), 7A = NPCs (monsters flagged as NPC in monstats; `npc_color`, defaults to the minion colour), 76/77/79.. = party / others. The game picks the colour in a routine around +0x72440 (switch on unit type). `me_color` / `minion_color` just overwrite those bytes each frame. There is one colour for the merc and all other minions.
- Level/Room structs (offsets we use): Level: pRoom2First +0x10, posX +0x1C, nextLevel +0x1AC, pMisc +0x1B4, levelNo +0x1D0. ActMisc: staffTombLevel +0x94, pAct +0x46C, pLevelFirst +0x47C. Room2: near rooms ptr +8, next +0x24, nearCount +0x2C, Room1 +0x30, pos +0x34/+0x38 (x5 = tiles), size +0x3C/+0x40, tiles +0x4C, level +0x58, presets +0x5C. Preset: txt +4, x +8, next +0xC, type +0x14 (1 monster, 2 object, 5 tile), y +0x18. Room1: coll map +0x20 (`{posX,posY,sizeX,sizeY,...,WORD* map at +0x20}`, bit 0 = blocked). Unit: mode +0x10, id +0xC, path +0x2C (item path x +0xC, y +0x10; player x/y WORDs at +2/+6), inventory +0x60, flags +0xC4 (0x04000000 = our "checked", 0x20000000 = our "revealed").
- Candidate patch sites for later work (from BH): item properties 0x2E3FC / 0x2E04B / 0x2E06D; always-show-items 0x1D74E, 0x1A89A, 0x4EA13, 0x4E61A, 0x63443. Verify each against
  the stock bytes and add a signature test before using it.

## Porting from BH (read this first)
Source: https://github.com/BeLikeLeBron/slashdiablo-maphack (AGPL-3.0). It answers most "how does the game do X" questions. `curl -L https://codeload.github.com/BeLikeLeBron/slashdiablo-maphack/tar.gz/refs/heads/master | tar xz` into the scratchpad and grep.
- `BH/D2Ptrs.h`: every FUNCPTR/ASMPTR/VARPTR lists **two** offsets per D2Client entry: the first is 1.13c, the **second is 1.13d** (what we target). E.g. `PrintGameString 0x7D850, 0x75EB0`, `GetItemName 0x914F0, 0x958C0`.
- `BH/BH.cpp` (top): the patch table `new Patch(Call|Jump, DLL, {1.13c, 1.13d}, stub, nbytes)`. Hook sites: GameLoop `{0x44230, 0x45280}` 7 bytes (Call), GameDraw `{0xC3DB4, 0x1D7B4}` 6 bytes (Jump). Stubs in `BH/D2Intercepts.cpp`.
- `BH/D2Structs.h`: struct layouts. Unit: dwType 0, dwTxtFileNo 4, pItemData/pPlayerData 0x14, pAct 0x1C, pPath 0x2C, dwFlags 0xC4, pListNext 0xE8. Act.pRoom1 +0x10. Room1: pUnitFirst +0x74, pRoomNext +0x7C. ItemData: quality 0, flags 0x18.
- Item alerts: `Modules/ItemMover/ItemMover.cpp` (packet 0x9c, action NEW_GROUND/OLD_GROUND) and `Modules/Maphack/Maphack.cpp` `OnDraw` ("Item Detailed Notifications", the one we ported: scans `act->pRoom1` rooms' unit lists, uses unit flag 0x04000000 as "checked", item flag 0x2000 as "new"). Rule: skip an action when `pingLevel > Ping Level`; `%NOTIFY-DEAD%` (0xdead) silences; colour = quality (none/inf/norm/sup white 0, magic 3, set 2, rare 9, unique 4, crafted 8); newlines in the name become " - ".
- Rule engine: `Modules/Item/ItemDisplay.cpp/.h`; item names `D2Helpers.cpp GetItemName`; automap/stat screens `Modules/Maphack`, `Drawing/Stats`, `Modules/ScreenInfo`; buffs/other features each have a folder under `BH/Modules`.
- The user's game folder has stock 1.13d DLLs to verify offsets against (the DLL file offset equals the RVA in .text; other sections differ, use the PE section table), plus BH config files that were used only to choose default colours/keys. Check any BH offset's bytes there before patching: BH's automap offset 0x73469 did **not** match stock bytes, ours (0x7349A) does.
- BH file layout is a good map of "where is feature X"; when adding a feature, find BH's module for it first.

## Drop alerts and item dots (done, confirmed in game)
`mh_install_loop` hooks the game loop (`sig_find_gameloop`); `mh_game_loop` -> `am_loop`, `id_tick`, queued chat, then every 100 ms `mh_scan_ground` -> `mh_alert_item(item, alert)`. A new/close item is evaluated once (unit flag 0x04000000 = checked): its matching map rules are stored in `g_dots` (up to 3, each with its own tier; flag 0x20000000 set) and, if alerting (`alert_close` or the item is new), printed with PrintGameString in the quality colour. `GetItemName` (+0x958C0) returns **no usable value**; test the buffer. `am_draw_dots` (automap hook) draws the marked items: rule tier is compared with the current tier level at draw time, as BH does. Only rules with a map action count (BH behaviour).

## Automap lines (ported from BH AutoTele, `src/automap.h`, `src/atvectors.h`)
BH's `Modules/AutoTele` is the source of the "lines to next / other / waypoint / previous" feature (BH config: Next Color, Other Color, WP Color, Prev Color, Other Extra Color). `atvectors.h` is BH's `Vectors.h` table (4 slots per area: next, other, waypoint, previous; generated by script; types 1 monster, 2 object, 5 tile, 6 exit, 7 xy, 8 exit+extra). Exit positions are tile presets (a tile whose destination level is the wanted one) or, for wilderness borders, computed exactly as BH does (`am_build_exits`, from `CollisionMap.h`): flood-fill the rooms connected to the player's room along the near-room lists, copy their collision data into a level-sized WORD map (unloaded rooms get their data added and removed again), `FillGaps` twice (a walkable cell without 3 walkable in a row both ways becomes blocked), take the first walkable run on each of the four outer edges, take its centre, and match it to the neighbouring level of the first different-level near room whose rectangle contains it. The map is freed right after; at most 3 attempts per level. Presets of unloaded rooms need `AddRoomData`/`RemoveRoomData` (BH FindPresetLocation adds a room only if it has no presets / tiles / Room1, but GetLevelExits adds EVERY room without a Room1: a room that already has some presets can still lack its stairs tile until added. A Catacombs level's next-stairs were never found until we followed the second rule for exits) with the **player's Room1** as the last argument (passing NULL found almost nothing). Look-ups run from the game loop, never in the draw hook: first 0.3 s after entering the level, then every 2 s (up to ~4 minutes) for as long as a target is unresolved; each attempt only looks at rooms not yet visited (`g_vis`, a room counts as visited once it had data or the add worked); drawing is at most 5 lines + squares.
The hiding of the game's own map text was blamed for map-open crashes for a long time; the real cause was the `stub_alloc` race (see Conventions). It is back and unconditional.

- Portals (`am_scan_portals`, `portal_color`): objects 59 / 60 (Portal, Portal) / 298 / 342 (Objects.txt rows named portal; 377 is the Guild Portal, not included). The game draws portals itself as automap *cells* (pictures) that cannot be recoloured, so we add our own line + square per portal, found by walking the act's rooms 2.5 times a second from `am_loop`, remembered as (unit, id) and re-validated each frame.

## Stats panel, hud, identify, keys
- Stats panel (`stats.h`): ported from `BH/Drawing/Stats/StatsDisplay.cpp` (no quest lines). Right side by default (the user's BH config had `Stats on Right: True`). Merc shown while the merc inventory (UI var 0x24) is open or after `stats_merc_key`.
- Hud (`hud.h`): clock top right when the map is closed (12 h without AM/PM by default), map info (name / difficulty / area level, blank when 0) when open.
- ItemText memory layout: BH's struct comments in `D2Structs.h` are wrong by +0x40 (it declares `wchar_t szName2[0x40]`, which is 0x80 bytes). Real offsets: code +0x80, speed +0xD8, locale name no. +0xF4, rangeadder +0x104, inventory width / height **+0x10F / +0x110**. The shift-click identify originally read +0xCF / +0xD0 and never matched an item.
- Item move (`idclick.h`, from BH `ItemMover::OnRightClick` / `LoadInventory` / `FindDestination`): Shift+right click: inventory -> stash (else open cube), stash -> open cube (else inventory), cube -> stash (else inventory); Ctrl+right click drops on the ground (BH's Ctrl+Shift -> closed cube is not ported; the cube item itself is never moved). When the cube panel is open it takes priority over the stash for clicks in its rectangle (it is drawn in the stash's place). It sends packet 0x19 (pick up, `SendPacket(5, 1, ..)`) then, 30 ms later from `mv_tick`, 0x18 (`{id, x, y, destination}`; destination 0 inventory / 3 cube / 4 stash) or 0x17 (`{id}`, drop). BH waits for the server's 0x9D reply instead (needs a recv hook). Free spot = first fit scanning column by column. After the put-down a move is only 'confirmed' once the cursor is empty again (`g_mv_wait_item`): until then further moves over the panels are swallowed (a second move planned on a grid the game has not updated yet picks the same free spot, the server refuses it and the item stays on the cursor: seen in a LAN game), and if the cursor still holds the item after 0.9 s it is put back at its source position. Occupancy grids are rebuilt from the player's items each click (position path+0xC/0x10, size txt+0x10F/0x110). The click is swallowed only when it lands on the inventory / stash panel.
- Identify (`idclick.h`): the inventory UI flag (UI var 1) is NOT set while the stash is open, so inventory items must not require it (BH only checks stash / cube items against their own panel).
- Identify (`idclick.h`): ported from BH ItemMover. Shift+click -> packet 0x20 (use tome) then, 30 ms later (the next game-loop tick) from the game loop, packet 0x27 {item, tome}. BH instead answers the server's 0x3F packet; we avoided a packet hook.
- Keys (`keys.h`): reload by typing `.reload` in chat (`reload_command`; the chat-send step at D2Client +0xB2342 (`call 0xB6890`, ESI = the packet being built, ANSI text at +3) is redirected to `qol_chat`, which returns -1 to swallow the line; BH's table lists 0xB24FF for this hook, which is a `PrintGameString` call in stock 1.13d, not the chat send),  filter level +/- (`=` `-` and numpad), stats `B`, Esc closes stats. The + / - keys change the filter level (BH "Filter Level", 0-3, what `FILTLVL` tests); the tier / ping level (`%TIER-n%`) is only set in the ini.

- Buff icons (`buffs.h`, from `BH/Modules/ScreenInfo`): polls `GetUnitState` (D2Common #10706) for the states in `bf_states` four times a second; draws along the bottom (buffs from x=117 upward in rows of 9, debuffs from the right), hover shows the name. Pictures: `build/qol_ui.mpq` (generated by `tools/make_qol_ui_mpq.py`, committed) holds `buffs24.dc6` with 52 frames of 24x24: BH's 45 (from BH's `buffs.mpq`, which is the game's skill icons scaled down) + 7 Druid ones made the same way from `DrSkillIcon.dc6` (d2exp.mpq; IconCel numbers from SkillDesc.txt: Barbs 4, Wolverine 10, Armageddon 50, Werewolf 20, Werebear 22, Feral Rage 54, Maul 56) quantised to the palette indices BH's frames use (Act1 `Pal.dat` from d2data.mpq). The DLL tries `qol_ui.mpq`, then BH's `buffs.mpq`; a frame the file lacks is drawn as a box. Frame number = row order of `bf_states`. Frame 34 (Meditation) is BH's picture with the bright disc shrunk to 78% (`shrink_disc` in the tool) so the stone background shows around it; BH's looked like it had no background. The archive is added with Storm #266 `SFileOpenArchive(path, 5000, 0, &h)` and the file loaded with D2Win #10023 `LoadCellFile`, drawn with D2gfx #10067 `DrawCellContextEx(ctx, x, y, -1, 5, tint)` (CellContext = 0x38 bytes: cell number at +0, CellFile* at +0x34). The extra Druid states are Spirit of Barbs 147, Heart of Wolverine 148, Armageddon 145, Werewolf 139, Werebear 140, Feral Rage 120, Maul 117. With no archive every state is drawn as a box with a two-letter tag. BH's Conviction special case (debuff when the fire resistance dropped) is not ported: Conviction always shows as a buff. Crash history: talking to Deckard Cain crashed the game (`Unrecoverable internal error` at an address inside D2CMP.dll, the cell decoder, found in the game's own `D2*.txt` log, not ours) until two changes: the generated DC6 now matches BH's file exactly (last frame's next-block pointer = file size, padding bytes 0xCD), and the CellContext passed to `DrawCellContextEx` is a zeroed static 0x100-byte buffer instead of a 0x40-byte stack array. Which of the two mattered was not tested; keep both. To add a state: add a frame to the MPQ tool and append to `bf_states` with that frame number (or -1 for a box).
- MPQ notes: BH's `buffs.mpq` entries are PKWARE-imploded; `tools/make_qol_ui_mpq.py` contains a decoder (explode), a DC6 reader/writer and an MPQ writer (v1, uncompressed files). Palette = `data\\global\\palette\\ACT1\\Pal.dat` (BGR).

## Performance notes
Item labels are cached per item (128 entries, 2 s TTL, bumped generation on reload and on area change); BH uses five LRU caches of 100 keyed by item id + flags with no expiry. Hud texts are built only when they change. The ground scan uses `readable_c`. Do not add per-frame walks over game unit lists.

## Debugging a crash
Set `logging=1`, reproduce, read the last lines of `qol_ui.log`: the `EXCEPTION` line gives the faulting module+offset and registers. Faults deep in game code with our frames absent usually mean a corrupted stub or a stack mismatch (calling convention), not the code at that address.

## Item stat ranges (`src/statrange.h`, from BH `Item::OnPropertyBuild`)
Hook: the call that builds ONE property line, D2Client +0x2E06D (`call 0x2CE40`, a userpurge function: EAX = stat number, ESI = the 128-wchar line buffer, stack = pItem, pStatList, nStatParam, nStatValue, `ret 0x10`). Unlike BH's stub (which reads dead stack slots after the call) ours saves the return address and the two arguments it needs BEFORE calling the original, then calls `sr_hook(nstat, wout, item, par)` which appends ` [min - max]` (colour `\377c<:>`, then back to `\377c3`). Ranges come from the game's tables in memory (all offsets verified against D2Common's own accessors): `sgptDataTable` = *(D2Common+0xA33F0); Properties +0xA4 (count +0xAC, record 0x2E: nFunc +0x18, wStat[7] +0x20); SetItems +0xC18 (count +0xC1C, record 0x1B8, 19 stats at +0x88); UniqueItems +0xC24 (count +0xC28, record 0x14C, 12 stats at **+0x8C**; BH's struct comment says 0x90); runewords via D2Common #10405 GetRunesTxt (record 0x120, stats +0xB0, rune-word id DWORD at +0x82) / #10981; magic affixes via #10174 GetItemMagicalMods (1-based, record 0x90, stats +0x24; `*(D2Common+0xA4CE4)` = first AutomMagic record); #10601 IsMatchingType. Results are cached per (item uid, stat, param). `item_stat_ranges=0` shows them only while Ctrl is held. NOT ported: BH's damage-line ranges (`OnDamagePropertyBuild`, a rewrite of the game's damage-line builder at +0x2E04B) and the "Base Defense [min - max]" line (`OnProperties`, a jump at +0x2E3FC).

## Player inspection (`src/inspect.h`, from BH `Item::OnKey` / `OnLoop` / `GetViewUnit` + `ViewInventoryPatch1-3`)
`inspect_key` (default 73 = I; the key is NOT blocked, so the game still toggles the inventory itself): with the mouse on another player / Iron Golem (291) / Valkyrie (357) / Shadow Master (418) the inventory panel shows that unit's gear. Handled on the game thread ~120 ms after the key (`g_iv_req` -> `iv_tick`): `GetSelectedUnit` (D2Client +0x17280), then `g_view_unit` is set and the inventory is opened with `SetUIVar(1, 0, 0)` (+0x1C190) if the key did not. Three spots that load "the player unit" while the inventory draws are redirected to stubs that call `iv_get()`: D2Client +0x997B2 (`mov esi,[player]`, 6 bytes), +0x98E84 (`mov ebx,[player]`, 6 bytes; its byte pattern also matches +0x9D1A4, so the signature includes the `sub esp,8 ; xor eax,eax ; cmp ecx,eax ; push ebx ; jne` prefix), +0x97E3F (`test eax,eax ; mov ecx,[edi+60h]`, 5 bytes; the stub swaps EDI only when `[edi]` != 1). The panel gets the unit's name drawn over it (BH reads `pPlayerData->szName` for every unit, which is garbage for golems; we use fixed names). While inspecting, left clicks at x >= 400 are swallowed and shift-ID / item-move are off. The inspection ends when the inventory closes or `FindServerSideUnit` (+0x620D0) no longer finds the unit.

## Always show items (`src/showitems.h`, from BH `Item` PermShowItems patches; same idea as Trihedraf/d2-item-labels)
Ground labels are drawn only while UI var 0xD (Alt, D2Client +0x11C8C4) is set. Four 6-byte reads of it are replaced by `E8 rel32 90` stubs (`sig_find_showitems`): +0x1D74E and +0x1A89A (`cmp [v],ebx`), +0x4EA13 (`mov eax,[esp+1Ch];test eax,eax`, end of the label loop, else it resets state), +0x63443 (`mov ecx,[v]`). Stubs test `g_show_items`: on = fake "set" (`test esp,esp` gives ZF=0; ecx=1), off = the original instruction. BH's 5th site (+0x4E61A, `jge`) is an identity while forced, so skipped. Patches are permanent, only the flag toggles (`show_items_key`, default L; `always_show_items` = start state). Not yet tested in game.
